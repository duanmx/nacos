## 1. 为什么需要鉴权体系

Nacos 客户端在每次与服务端通信时（注册实例、订阅服务、查询配置等），都需要携带身份凭证。不同类型的凭证（用户名/密码、AccessKey/SecretKey、RAM、OIDC Token）由不同的鉴权插件处理。

**鉴权体系的核心问题**：

1. **凭证来源多样**：用户可能使用用户名/密码、AK/SK、RAM 角色、OIDC 等多种方式
2. **Token 有生命周期**：accessToken 可能过期，需要支持重新登录
3. **请求透明注入**：gRPC、HTTP 等不同通信协议都需要携带鉴权 Header
4. **插件化扩展**：企业用户可能需要自定义鉴权逻辑（如对接内部 SSO）

Nacos 的解决方案是：**SPI 插件化 + 门面模式**。

## 2. 架构总览：四层鉴权链

```
┌────────────────────────────────────────────────────────────────────┐
│  第 1 层：通信代理层（每次 RPC/HTTP 调用前调用 getSecurityHeaders）│
│  AbstractNamingClientProxy / AbstractLockClient / AiGrpcClient     │
├────────────────────────────────────────────────────────────────────┤
│  第 2 层：鉴权门面（统一对外接口）                                 │
│  SecurityProxy                                                     │
│  ├─ login(Properties)         ← 驱动所有插件执行登录              │
│  ├─ getIdentityContext(resource) ← 汇聚所有插件的 Token           │
│  ├─ reLogin()                 ← Token 过期标记                    │
│  └─ shutdown()                ← 关闭所有插件                      │
├────────────────────────────────────────────────────────────────────┤
│  第 3 层：SPI 插件管理器                                            │
│  ClientAuthPluginManager                                           │
│  ├─ init(serverList, restTemplate)  ← SPI 加载所有插件            │
│  ├─ refreshServerList(serverList)    ← 服务端地址变更时刷新        │
│  └─ getAuthServiceSpiImplSet()       ← 返回所有插件实例            │
├────────────────────────────────────────────────────────────────────┤
│  第 4 层：鉴权插件实现（SPI）                                      │
│  AbstractClientAuthService → ClientAuthService                     │
│  ├─ DefaultClientAuthServiceImpl   (用户名/密码 → 登录获取 Token) │
│  ├─ RamClientAuthServiceImpl       (RAM 角色 → STS Token)         │
│  └─ 自定义插件                      (企业 SSO / LDAP / OIDC)      │
└────────────────────────────────────────────────────────────────────┘
```

**为什么分四层？**

- 第 1 层关注"每次请求别忘了带 Token"，嵌入到通信协议层
- 第 2 层关注"统一管理 Token"，对外隐藏多插件细节
- 第 3 层关注"加载哪些插件"，用 SPI 机制解耦
- 第 4 层关注"如何获取 Token"，各插件独立实现

## 3. SecurityProxy：鉴权门面

### 3.1 构造与初始化

> 源码：[SecurityProxy.java](file:///Users/mmhm/IdeaProjects/nacos/client/src/main/java/com/alibaba/nacos/client/security/SecurityProxy.java) L108-124

```java
public SecurityProxy(AbstractServerListManager serverListManager,
    NacosRestTemplate nacosRestTemplate) {
    // Step 1: 创建 SPI 插件管理器
    clientAuthPluginManager = new ClientAuthPluginManager();
    // Step 2: 初始化插件（加载 SPI 实现 + 注入服务端列表 + HTTP 模板）
    clientAuthPluginManager.init(serverListManager.getServerList(), nacosRestTemplate);

    NotifyCenter.registerSubscriber(new Subscriber<ServerListChangeEvent>() {
        @Override
        public void onEvent(ServerListChangeEvent event) {
            clientAuthPluginManager.refreshServerList(
                serverListManager.getServerList());
        }
        @Override
        public Class<? extends Event> subscribeType() {
            return ServerListChangeEvent.class;
        }
    });
}
```

### 3.2 login()：驱动所有插件登录

> 源码：[SecurityProxy.java](file:///Users/mmhm/IdeaProjects/nacos/client/src/main/java/com/alibaba/nacos/client/security/SecurityProxy.java) L140-148

```java
public void login(Properties properties) {
    if (clientAuthPluginManager.getAuthServiceSpiImplSet().isEmpty()) {
        return;  // 没有 SPI 插件 → 无需登录（如未配置用户名/密码）
    }
    for (ClientAuthService clientAuthService : clientAuthPluginManager
        .getAuthServiceSpiImplSet()) {
        clientAuthService.login(properties);  // 各插件使用 properties 中的凭证登录
    }
}
```

**登录凭证从哪里来？**

用户通过 `Properties` 传递给 `NacosNamingService` / `NacosConfigService` 构造器：

```java
Properties properties = new Properties();
properties.put("username", "nacos");
properties.put("password", "nacos");
NacosNamingService naming = new NacosNamingService(properties);
```

这些 `Properties` 最终通过调用链传递到 `SecurityProxy.login(properties)`，各插件从 `properties` 中提取自己需要的凭证。

### 3.3 getIdentityContext()：汇聚所有插件的 Token

> 源码：[SecurityProxy.java](file:///Users/mmhm/IdeaProjects/nacos/client/src/main/java/com/alibaba/nacos/client/security/SecurityProxy.java) L167-178

```java
public Map<String, String> getIdentityContext(RequestResource resource) {
    Map<String, String> header = new HashMap<>(1);
    for (ClientAuthService clientAuthService : clientAuthPluginManager
        .getAuthServiceSpiImplSet()) {
        LoginIdentityContext loginIdentityContext =
            clientAuthService.getLoginIdentityContext(resource);
        // 遍历该插件的所有 key，合并到 header Map
        for (String key : loginIdentityContext.getAllKey()) {
            header.put(key, loginIdentityContext.getParameter(key));
        }
    }
    return header;
}
```

**合并策略**：遍历所有插件，将各插件的 `LoginIdentityContext` 中的 key-value 全部放进同一个 Map。如果多个插件有相同的 key，后者覆盖前者。

### 3.4 reLogin()：Token 过期标记

> 源码：[SecurityProxy.java](file:///Users/mmhm/IdeaProjects/nacos/client/src/main/java/com/alibaba/nacos/client/security/SecurityProxy.java) L196-212

```java
public void reLogin() {
    if (clientAuthPluginManager.getAuthServiceSpiImplSet().isEmpty()) {
        return;
    }
    for (ClientAuthService clientAuthService : clientAuthPluginManager
        .getAuthServiceSpiImplSet()) {
        try {
            LoginIdentityContext loginIdentityContext =
                clientAuthService.getLoginIdentityContext(new RequestResource());
            if (loginIdentityContext != null) {
                // 关键：设置 RELOGINFLAG 标记，通知插件下次请求时重新登录
                loginIdentityContext.setParameter(
                    NacosAuthLoginConstant.RELOGINFLAG, "true");
            }
        } catch (Exception e) {
            LOGGER.error("[SecurityProxy] set reLoginFlag failed.", e);
        }
    }
}
```

**关键设计：reLogin() 只是设置标记，不立即登录**

> 源码：[NacosAuthLoginConstant.java](file:///Users/mmhm/IdeaProjects/nacos/client-basic/src/main/java/com/alibaba/nacos/client/auth/impl/NacosAuthLoginConstant.java) L40

```java
public static final String RELOGINFLAG = "reLoginFlag";
```

`reLogin()` 只在 `LoginIdentityContext` 中设置 `reLoginFlag=true`，不立即发起登录请求。**为什么？**

1. **避免阻塞调用方**：`reLogin()` 是由 gRPC/HTTP 请求的 403 响应触发，此时网络线程正在处理请求。如果 `reLogin()` 立即同步发起 HTTP 登录请求，会阻塞网络线程
2. **懒加载思想**：下一次 `getIdentityContext(resource)` 时，插件检测到 `RELOGINFLAG=true`，此时才真正发起重新登录

## 4. ClientAuthPluginManager：SPI 插件加载

> 源码：[ClientAuthPluginManager.java](file:///Users/mmhm/IdeaProjects/nacos/plugin/auth/src/main/java/com/alibaba/nacos/plugin/auth/spi/client/ClientAuthPluginManager.java) L36-92

```java
public class ClientAuthPluginManager implements Closeable {
    private final Set<ClientAuthService> clientAuthServiceHashSet = new HashSet<>();

    public void init(List<String> serverList, NacosRestTemplate nacosRestTemplate) {
        // 通过 Java SPI 加载所有 AbstractClientAuthService 实现
        Collection<AbstractClientAuthService> clientAuthServices =
            NacosServiceLoader.load(AbstractClientAuthService.class);
        for (ClientAuthService clientAuthService : clientAuthServices) {
            // 注入运行时依赖
            clientAuthService.setServerList(serverList);
            clientAuthService.setNacosRestTemplate(nacosRestTemplate);
            clientAuthServiceHashSet.add(clientAuthService);
        }
    }

    public void refreshServerList(List<String> serverList) {
        for (ClientAuthService clientAuthService : clientAuthServiceHashSet) {
            clientAuthService.setServerList(serverList);
        }
    }

    public Set<ClientAuthService> getAuthServiceSpiImplSet() {
        return clientAuthServiceHashSet;
    }
}
```

**SPI 加载的是什么类？**

> 源码：[ClientAuthPluginManager.java](file:///Users/mmhm/IdeaProjects/nacos/plugin/auth/src/main/java/com/alibaba/nacos/plugin/auth/spi/client/ClientAuthPluginManager.java) L50-51

```java
Collection<AbstractClientAuthService> clientAuthServices = NacosServiceLoader
    .load(AbstractClientAuthService.class);
```

注意：这里加载的是 `AbstractClientAuthService`（抽象类），而非 `ClientAuthService`（接口）。这是 Nacos SPI 的一个特殊设计——通过抽象类来要求插件实现方继承基类，以获得 `setServerList`、`setNacosRestTemplate` 等公共方法的默认实现。

## 5. ClientAuthService：鉴权插件接口

> 源码：[ClientAuthService.java](file:///Users/mmhm/IdeaProjects/nacos/plugin/auth/src/main/java/com/alibaba/nacos/plugin/auth/spi/client/ClientAuthService.java) L32-65

```java
public interface ClientAuthService extends Closeable {

    /** 使用 Properties 中的凭证登录 */
    Boolean login(Properties properties);

    /** 注入服务端地址列表（登录请求需要知道往哪发） */
    void setServerList(List<String> serverList);

    /** 注入 HTTP 请求模板（登录请求走 HTTP） */
    void setNacosRestTemplate(NacosRestTemplate nacosRestTemplate);

    /** 获取当前插件的登录身份上下文（含 accessToken 等） */
    LoginIdentityContext getLoginIdentityContext(RequestResource resource);
}
```

**`LoginIdentityContext` 是什么？**

这是一个 key-value 容器，存储登录后获得的鉴权参数：

```
DefaultClientAuthServiceImpl 的 LoginIdentityContext：
  ├─ "accessToken" → "eyJhbGciOiJIUzI1NiJ9..."
  ├─ "tokenTtl"    → "18000"
  └─ "reLoginFlag"  → "false"  (由 SecurityProxy.reLogin() 设置为 "true")

RamClientAuthServiceImpl 的 LoginIdentityContext：
  ├─ "accessKeyId"  → "LTAI5t..."
  ├─ "accessKeySecret" → "..."
  ├─ "securityToken" → "STS..."  (RAM 角色的临时 token)
```

**为什么 `LoginIdentityContext` 是插件粒度的而不是全局的？**

每个插件有自己独立的 `LoginIdentityContext`，互不干扰。`SecurityProxy.getIdentityContext()` 遍历所有插件，合并成一个 Map。这样设计的好处是：

1. 多租户场景：同时使用默认用户名/密码鉴权 + RAM 鉴权
2. 降级：某个插件的 Token 过期不影响其他插件的正常请求

## 6. 鉴权注入链：每次请求如何携带 Token

### 6.1 Naming 模块的注入链

> 源码：[AbstractNamingClientProxy.java](file:///Users/mmhm/IdeaProjects/nacos/client/src/main/java/com/alibaba/nacos/client/naming/remote/AbstractNamingClientProxy.java) L116-126

```java
protected Map<String, String> getSecurityHeaders(String namespace, String group,
    String serviceName) {
    // Step 1: 通过 SecurityProxy 获取 accessToken 等鉴权信息
    RequestResource resource = RequestResource.namingBuilder()
        .setNamespace(namespace)
        .setGroup(group)
        .setResource(serviceName)
        .build();
    Map<String, String> result = this.securityProxy.getIdentityContext(resource);
    // Step 2: 追加 app 标识头
    result.putAll(getAppHeaders());
    return result;
}

protected Map<String, String> getAppHeaders() {
    Map<String, String> result = new HashMap<>(1);
    result.put("app", AppNameUtils.getAppName());
    return result;
}
```

**注入链完整路径**：

```
每次 gRPC 请求：
  NamingGrpcClientProxy.requestToServer(Request)
    → request.putAllHeader(getSecurityHeaders(namespace, group, serviceName))
      → SecurityProxy.getIdentityContext(resource)
        → 遍历所有 ClientAuthService → 获取 LoginIdentityContext → 合并 Header
      → getAppHeaders() → 追加 "app": {AppName}
    → rpcClient.request(request)  ← gRPC Metadata 携带 accessToken + app

每次 HTTP 请求：
  NamingHttpClientProxy.callServer()
    → Map<String, String> headers = getSecurityHeaders(...)
    → nacosRestTemplate.exchange(url, headers, ...)  ← HTTP Header 携带 accessToken
```

### 6.2 Config 模块的注入链

Config 模块也使用 `SecurityProxy`，但注入方式略有不同。Config 的 `ConfigRpcTransportClient` 在创建 `RpcClient` 时，通过 `requestProxy()` 方法注入鉴权信息。每次 `ConfigBatchListenRequest` / `ConfigQueryRequest` 发送前，鉴权 Header 被注入到 gRPC Metadata。

### 6.3 为什么每次请求都要重新调用 getIdentityContext()？

**因为 Token 可能在两次请求之间过期并刷新。** 如果缓存 Token Map，当 `reLogin()` 设置 `RELOGINFLAG=true` 并触发重新登录后，缓存的旧 Map 仍然包含过期的 accessToken。每次都重新获取保证拿到最新的 Token。

## 7. 403 重新登录机制

### 7.1 触发场景

当服务端返回 403 Forbidden 时，说明 accessToken 可能已过期。客户端需要触发重新登录并重试请求。

### 7.2 Naming gRPC 的 403 处理

`NamingGrpcClientProxy.requestToServer()` 中，gRPC 请求返回的 `Response` 包含错误码。当错误码为 403 时：

```
NamingGrpcClientProxy.requestToServer()
  → Response response = rpcClient.request(request)
  → if (response.getErrorCode() == 403) {
        reLogin();  // → securityProxy.reLogin() → 设置 RELOGINFLAG=true
        // 下一次 getIdentityContext() 时检测到 RELOGINFLAG → 触发实际登录
    }
```

### 7.3 Naming HTTP 的 403 处理

`NamingHttpClientProxy.callServer()` 中的 HTTP 请求返回 403 状态码时，同样调用 `reLogin()` 触发 Token 刷新。

### 7.4 为什么 403 时 reLogin() 不立即登录而是标记方式？

**决策理由总结**：

1. **避免阻塞网络线程**：403 响应在 gRPC/HTTP 的网络 IO 线程中被检测到，如果 `reLogin()` 内立即发起同步 HTTP 登录请求，会阻塞网络线程
2. **延迟到下次实际请求**：登录请求本身也需要网络 IO，如果当前网络不可达（可能是网络问题导致 403），立即登录也会失败。延迟到下次请求时可以复用已恢复的连接
3. **避免重复登录**：如果短时间内多个请求同时收到 403，标记方式保证只登录一次（`RELOGINFLAG` 是一个 boolean 标志，多次设置效果相同）

## 8. 服务端地址变更自动刷新

> 源码：[SecurityProxy.java](file:///Users/mmhm/IdeaProjects/nacos/client/src/main/java/com/alibaba/nacos/client/security/SecurityProxy.java) L112-123

```java

            serverListManager.getServerList());
    }

```

**触发时机**：当 `NamingServerListManager` 或 `ConfigServerListManager` 检测到服务端地址列表发生变化时（如新节点上线、旧节点下线），发布 `ServerListChangeEvent`。

**为什么需要这个机制？**

登录请求（`/v1/auth/login`）需要发 HTTP 请求到 Nacos 服务端。如果服务端地址列表变了（如集群扩容），鉴权插件仍向老地址发登录请求会失败。通过监听 `ServerListChangeEvent`，及时更新插件中的服务端列表，确保登录请求发到正确的地址。

## 9. 多模块使用 SecurityProxy 的差异

| 维度 | Naming | Config | Lock |
|------|--------|--------|------|
| **SecurityProxy 持有者** | NamingClientProxyDelegate | NacosConfigService | NacosLockService |
| **鉴权注入位置** | AbstractNamingClientProxy.getSecurityHeaders() | ConfigRpcTransportClient.requestProxy() | AbstractLockClient.getSecurityHeaders() |
| **注入方式** | gRPC Metadata + HTTP Header | gRPC Metadata | gRPC Metadata |
| **403 处理** | gRPC: requestToServer 中检测 | gRPC: requestProxy 中检测 | 同 Naming |
| **app 头注入** | ✅（getAppHeaders） | ❌ | ❌ |

**为什么 Naming 需要 app 头而 Config 不需要？**

> 源码：[AbstractNamingClientProxy.java](file:///Users/mmhm/IdeaProjects/nacos/client/src/main/java/com/alibaba/nacos/client/naming/remote/AbstractNamingClientProxy.java) L76, L133-136

```java
private static final String APP_FILED = "app";

protected Map<String, String> getAppHeaders() {
    Map<String, String> result = new HashMap<>(1);
    result.put(APP_FILED, AppNameUtils.getAppName());
    return result;
}
```

Naming 模块的服务端需要通过 `app` 头来区分不同应用的请求，用于实现**按应用隔离**（同一个 Nacos 集群中，应用 A 不能看到应用 B 注册的实例）。Config 模块的配置隔离通过 namespace + group 完成，不需要额外的 app 标识。

## 10. 关键设计决策

### 10.1 为什么用门面模式（SecurityProxy）而不是让各模块直接调用插件？

**决策理由**：

1. **统一入口**：login、reLogin、shutdown 等操作需要跨越所有插件统一执行，门面保证了一致性
2. **横切关注点**：服务端地址变更监听（`ServerListChangeEvent`）是一个横切关注点，放在门面中一处注册，避免在 Naming/Config/Lock 三处重复
3. **Header 合并**：`getIdentityContext()` 需要遍历所有插件、合并 Header Map，这个逻辑放在门面中比放在各通信模块中更合适

### 10.2 为什么 SPI 加载的是 AbstractClientAuthService 而不是 ClientAuthService？

**决策理由**：

`AbstractClientAuthService` 提供了 `setServerList` 和 `setNacosRestTemplate` 的默认实现（通常是存到成员变量）。如果加载的是接口 `ClientAuthService`，客户端无法保证插件实现类一定有这些 setter（接口只定义了方法签名，不强制实现类有对应的成员变量）。抽象类可以持有 `serverList` 和 `nacosRestTemplate` 成员变量，避免每个插件实现类重复写 setter。

### 10.3 为什么 reLogin 是标记而非立即登录？

**决策理由**（前面已详述）：避免阻塞网络线程 + 延迟到下次请求 + 避免重复登录。这是典型的"惰性求值"（Lazy Evaluation）模式在分布式鉴权场景中的应用。

### 10.4 为什么每次请求都重新获取 IdentityContext？

**决策理由**：Token 可能在两次请求之间过期并被 `reLogin()` 刷新。如果缓存上一次的 `getIdentityContext()` 结果，后续请求可能携带已过期的 Token。虽然每次重新获取有轻微的性能开销（遍历插件集合），但插件内部的 `LoginIdentityContext` 已经是缓存的结果，无需每次发起网络请求。

### 10.5 为什么服务端地址变更要通知鉴权插件？

**决策理由**：登录请求是发往 Nacos 服务端的 HTTP 请求（`POST /v1/auth/login`）。如果服务端集群扩容/缩容，鉴权插件内部缓存的 serverList 如果不更新，登录请求可能发往已经下线的节点，导致登录失败 → 后续所有业务请求都因缺少 Token 而 403。

## 11. 总结

### 11.1 完整鉴权交互时序

```
初始化阶段：
  NacosNamingService(properties)
    → NamingClientProxyDelegate 构造
      → new SecurityProxy(serverListManager, restTemplate)
        → ClientAuthPluginManager.init()
          → NacosServiceLoader.load(AbstractClientAuthService)
          → 注入 serverList + restTemplate
        → NotifyCenter.registerSubscriber(ServerListChangeEvent)
      → securityProxy.login(properties)
        → 遍历各插件 → clientAuthService.login(properties)
          → DefaultClientAuthServiceImpl:
            POST /v1/auth/login {username:"nacos", password:"nacos"}
            → 服务端返回 accessToken
            → 存入 LoginIdentityContext

运行时阶段（每次 RPC 调用）：
  NamingGrpcClientProxy.requestToServer(request)
    → getSecurityHeaders(namespace, group, serviceName)
      → securityProxy.getIdentityContext(resource)
        → 遍历各插件 → 获取 LoginIdentityContext
        → 合并 Header: {"accessToken": "eyJ...", "app": "myApp"}
    → request.putAllHeader(headers)
    → rpcClient.request(request)  ← gRPC Metadata 携带鉴权信息

403 重新登录：
  服务端返回 403
    → reLogin() → securityProxy.reLogin()
      → 遍历各插件 → loginIdentityContext.setParameter("reLoginFlag", "true")
    → 下一次 getIdentityContext(resource) 时
      → 插件检测到 RELOGINFLAG=true
        → 发起 HTTP 登录请求 → 获取新 accessToken

服务端地址变更：
  ServerListChangeEvent 发布
    → SecurityProxy 中的 Subscriber 收到
      → clientAuthPluginManager.refreshServerList(newList)
        → 遍历各插件 → clientAuthService.setServerList(newList)
```
